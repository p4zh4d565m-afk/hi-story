## A6. 章节历史去掉 7 天过期

### 1. 修改目标

正文历史覆盖成书周期，而不是一周。

### 2. 当前问题

`ChapterHistoryRepo.addSnapshot` 在写入后执行：

```ts
const MAX_SNAPSHOT_AGE_DAYS = 7;
DELETE FROM chapter_history WHERE chapter_id = ? AND saved_at < ?
```

50 万字是数月工程。超过 7 天的快照会被清掉，无法回答「这章上个月什么样」。

### 3. 修改方式

- 删除（或永久禁用）按时间 `DELETE` 的那段逻辑。
- **保留** `MAX_SNAPSHOTS_PER_CHAPTER = 30`：按时间淘汰最旧，防止每章无限增长。50 万字 × 30 份快照仍是桌面可接受量级。
- 不改恢复 UI（`WritingArea` 已有历史面板）。

若确认时要求「连 30 份上限也取消」，改为 200，并在方案确认里写明；默认不取消。

### 4. 涉及文件

| 文件 | 动作 |
|---|---|
| `src/main/db/repositories/chapter.repo.ts` | 去掉 `MAX_SNAPSHOT_AGE_DAYS` 及对应 DELETE |
| `tests/unit/db/chapter-history.test.ts` | **新建**：写入一份 `saved_at` 为 8 天前的快照，再 `addSnapshot`，断言旧快照仍在；超过 30 份时最旧被删 |

### 5. 可能风险

- 磁盘占用上升（可接受）。已超过 7 天、**已经被删掉**的历史无法找回。
- 历史面板条目变多，滚动即可，不必改 UI。

### 6. 是否影响已有数据

- **不改已有行。** 只停止继续按时间删除。
- 过去 7 天内仍在的快照会留下来，并开始超过 7 天继续留。

### 7. 是否需要迁移

**否。** 只改运行时清理策略，无 DDL。

## M1. OpenAI 兼容路径读取 `options.systemPrompt`

### 1. 修改目标

国内常用的 OpenAI 兼容供应商（DeepSeek、豆包、通义、Moonshot、智谱、自定义）与 Claude 一样合并 `ChatOptions.systemPrompt`。起名助手依赖该字段。

### 2. 当前问题

`claude.ts` 会把 `options.systemPrompt` 拼到 system。`generic-openai.ts` 的 `chat` 和 `chatStream` **全文不读**该字段，只把 `messages` 原样送出。`NameGenerator.tsx` 约 502–505 行把指令放在 `systemPrompt` 而不是 messages。非 Claude 起名等于丢系统指令。

### 3. 修改方式

抽出与 Claude 同语义的纯函数，两处 provider 共用：

```ts
export function mergeSystemPrompt(messages: ChatMessage[], extra?: string): ChatMessage[] {
  if (!extra) return messages;
  const system = messages.filter(m => m.role === 'system');
  const rest = messages.filter(m => m.role !== 'system');
  return [{ role: 'system', content: extra + (system.length ? '\n\n' + system.map(m => m.content).join('\n\n') : '') }, ...rest];
}
```

`GenericOpenAIProvider.chat` / `chatStream` 在组请求前调用。Claude 改为走同一函数，避免两套拼接。

单测只测 `mergeSystemPrompt`：无 extra 不改；有 extra 且已有 system 则前缀；有 extra 无 system 则插入一条。

| `src/main/ai/providers/generic-openai.ts` | chat + chatStream 使用 |

## A3. `planning_ideas` 唯一约束 + 坏 JSON 失败可见 + save 禁止缺省清空

### 1. 修改目标

一项目一行策划圣经。读失败要报错，不能假装「没纲」。`save` 漏传字段不得把已有总纲/分卷/章纲写成空。

### 2. 当前问题

- 仅有普通索引 `idx_planning_ideas_project`，无 `UNIQUE(project_id)`。
- `findByProject` / `save`：`ORDER BY updated_at DESC LIMIT 1`。
- Obsidian 导入：`rows.length > 1` 直接抛错。
- `buildTargetState`：`planningRows[0]`，无排序。
- `rowToPlanningIdea`：`JSON.parse` 失败 catch 成 `[]` / `null`。
- `save`：`input.volumeOutlines ?? []`，未传即清空。

### 3. 修改方式

**（1）迁移 v20：去重 + 唯一索引**

在同一事务内：

1. 每个 `project_id` 只留 `updated_at DESC, id DESC` 的第一行，其余 DELETE。
2. `CREATE UNIQUE INDEX IF NOT EXISTS idx_planning_ideas_project_id ON planning_ideas(project_id);`
3. 可保留旧非唯一索引（无害）或删掉，避免优化器混淆。建议删除 `idx_planning_ideas_project`（若存在且与新索引重复）。

**（2）解析失败可见**

抽出 `parsePlanningJson(row)`：任一 JSON 列非法 → `findByProject` / `findById` 返回 `{ success: false, error: '策划数据损坏，请从备份或 Obsidian 重新导入' }`。禁止返回空纲冒充成功。

**（3）save 改为读-改-写合并（必须区分 `undefined` 与 `null`）**

`SavePlanningIdeaInput` 中 `masterOutline` / `volumeOutlines` / `chapterOutlines` / `generatedOptions` 等 JSON 字段改为可选。

**禁止用 `??` 合并。** 现有 `input.volumeOutlines ?? []` 会把 `null` 和 `undefined` 都吞成 `[]`，导致「未传」和「想清空」分不开。

实现约定：

| 调用方传入 | 含义 | 落库 |
|---|---|---|
| 字段不出现（`=== undefined`） | 未传，保留旧值 | 用库里已有 JSON |
| `null` | 显式清空对象型（如总纲） | 写成 `''` / `null` |
| `[]` | 显式清空数组型（分卷/章纲/方案） | 写成 `'[]'` |
| 非空对象/数组 | 替换 | `JSON.stringify(新值)` |

```ts
function pickJsonField<T>(incoming: T | null | undefined, existing: T): T | null {
  if (incoming === undefined) return existing;
  return incoming; // null 或 [] 或新值都按字面落库
}
```

单测必须覆盖三分支，缺一不可：省略字段、`null`、`[]`。当前 `PlanningWorkspace.save` 仍传全量，行为不变。

`findByProject` 在唯一约束后可改为 `WHERE project_id = ?` 单行，不必再 `ORDER BY LIMIT 1`。Obsidian 的「多行抛错」可改为依赖 UNIQUE，插入冲突即失败。

### 4. 涉及文件

| 文件 | 动作 |
|---|---|
| `src/main/db/migrations.ts` | 新增 version 20 |
| `src/main/db/repositories/planning.repo.ts` | 解析失败返回 error；save 合并；按 project_id 精确查找 |
| `src/main/db/repositories/obsidian-import.repo.ts` | `buildTargetState` 与 `applyPlanning` 与唯一行对齐（仍可保留多行防御） |
| `src/renderer/types/index.ts` | `SavePlanningIdeaInput` 若导出则标可选字段（类型现定义在 repo） |
| `tests/unit/db/planning.repo.test.ts` | **新建**：重复插入失败；坏 JSON 返回 success:false；save **省略** volumeOutlines 时旧值仍在；显式 `null`/`[]` 才清空 |
| `CLAUDE.md` / `AGENTS.md` | 实施时补一句 v20（确认执行后才改文档） |

### 5. 可能风险

- 若某项目真有两行策划，迁移会丢掉较旧那一行。应用当前读写语义本来就只认最新行，与日常 UI 一致；Obsidian 导入此前会因多行失败，去重后导入反而能工作。
- save 合并后，若某调用方想清空却漏传字段，将清不掉。这是故意的。清空必须显式传 `[]` / `null`。`PlanningWorkspace` 重生成总纲时已经显式传空分卷/章纲，保持不变。

### 6. 是否影响已有数据

- **有。** 同一 `project_id` 的多余行会被删除，只留最新一行。
- 合法单行项目无变化。
- 已损坏 JSON 从「打开是空的」变成「打开报错」，数据仍在库里，只是不再静默丢。

### 7. 是否需要迁移

**是。v20。** 必须先去重再加 UNIQUE，否则已有重复行的库会迁移失败。

## A2. 策划 AI 长任务完成后校验项目

### 1. 修改目标

切到另一项目后，A 的生成结果不得画到 B 的界面上；也不得用 B 的确认把 A 的方案写入 B。

### 2. 当前问题

`PlanningWorkspace` 在 `App` 里常驻。`generate` / `generateMasterOutline` / 分卷生成 / 章纲生成在 `await aiService.chat` 之后无条件 `setState` + `save()`。

`save` 闭包里的 `project.id` 是点击时的项目（写入 A 其实合理），但 `setOptions` 作用在当前实例上（B 的 UI）。用户再点确认，会用 **B 的 projectId + A 的 options** 写库。

读路径已有 `currentProjectIdRef` + generation；写路径没有。

### 3. 修改方式

抽出两个函数，便于单测、避免改 UI 结构：

```ts
function shouldApplyPlanningResult(startedProjectId: string, currentProjectId: string | null): boolean {
  return currentProjectId === startedProjectId;
}
```

每个生成函数开头：`const startedId = project.id`。

每个 `await` 之后（Skill 路由、skills:get、ai.chat、parse 之后）：

- 若 `!shouldApplyPlanningResult(startedId, currentProjectIdRef.current)`：
  - **仍然**把结果 `save` 到 `startedId`（后台写完 A 的策划，不浪费已生成内容）。
  - 为此把持久化从「闭包 `project.id` + 一堆 setState」拆成 `persistPlanning(projectId, payload)`，只 IPC、不 setState。
  - 然后 `return`，不 `setOptions` / `setMasterOutline` 等。
- 若仍是同一项目：现有 `setState` + `save`。

`confirm` 本身是同步点击，用当前 `project.id`，只要界面没被 A 的结果污染就不会写错。本改动的关键是挡住 `setState`。

`save` 失败时的 `setError` 同样要过项目门禁。

`configureFirstAi` 与 Chat 抢 `aiService` 单例不在本轮范围（B10）。

## A1. AI 写章落库改为 create 返回 ID 后同步写入

### 1. 修改目标

生成正文、摘要、事实必须写进**刚创建的那一章**，不靠 `sortOrder`、不靠 `setTimeout`、不靠 `localStorage` 传 payload。

### 2. 当前问题

`App.tsx` `onSaveAsChapter`：

1. `handleCreateChapter(title)` 返回 `void`，调用方拿不到 id。
2. `setTimeout(300)` 后 `findByProject`，按最大 `sortOrder` 猜章节。
3. 再套 500/800/1000ms 写 summary / facts / hooks，不检查 `success`。
4. `AIWritePanel` 把抽取结果放进 `hi-story-pending-summary`，与保存脱节。批量生成时多章会抢同一把 localStorage 钥匙。

`db:chapter:create` 已支持 `content` 和 `planningOutline`，当前创建时 content 为空、word_count=0。

### 3. 修改方式

**（1）`handleCreateChapter` 返回 `Chapter | null`**

创建后检查 `res.success` 与 `isActiveProject`。失败返回 null，不改本地 chapters。

**（2）`onSaveAsChapter` 改为同步链路**

签名建议：

```ts
onSaveAsChapter: (input: {
  title: string;
  content: string;
  planningOutline?: ChapterOutline | null;
}) => Promise<string | null>  // 返回 chapterId
```

实现：

1. `create({ projectId, title, content, planningOutline: pendingAIOutlineRef.current })`
2. 若成功：`setChapters`、`setActiveChapterId`、清 pending 章纲。
3. 计算字数：立即 `db:chapter:update({ id, content, wordCount })`（复用 `handleSaveChapter`，它已检查 success）。`create` 若已写入 content，update 仍用于字数；若 create 能算 word_count 更干净——在 `ChapterRepo.create` 里用与渲染端相同的 CJK 计数，避免二次 update。优先在 repo create 时写入 word_count，渲染端只 setState。
4. 返回 `chapter.id`。失败返回 null。全程无 `setTimeout`。

**（3）抽取不再走 localStorage**

`AIWritePanel.handleSave` / `runBatch`：

1. `const chapterId = await onSaveAsChapter(...)`
2. 若无 id，提示保存失败，不抽。
3. `generateAndSaveSummary` 改为接收 `chapterId`，抽取成功后调用新的 `onPersistExtraction(chapterId, { summary, facts, knowledge })`。

`onPersistExtraction`（App 内，必须带启动时的 projectId）：

- `db:chapter:update({ id: chapterId, summary })`，检查 success。

## A5. 钩子单轨：抽取进待确认，停止双写

> **产品补记（2026-09-12）：** 标题原作「钩子/债务单轨」过满。写章抽取 prompt（`FACT_EXTRACTION_SYSTEM_PROMPT`）只有 `factType=hook`，旧旁路也只双写钩子、从不自动建债务。本轮只收口钩子。债务已能从**对话决策账本**提议确认；写章自动抽债务是独立 P2（需改抽取 prompt + 类型 + `factsToDebtDrafts`），不补不算丢数据。

### 1. 修改目标

新产生的叙事钩子只进入 `narrative_hooks` 这一条权威（经决策账本确认）。写章抽取不再 `story_facts(hook)` + `narrative_hooks.create` 无关联双写。旧伏笔表不再接收新的自动数据。写章路径不抽、不映射、不写入 `narrative_debts`。

### 2. 当前问题

- 写章旁路：facts 含 `factType=hook` 写入 `story_facts`，再对每个 hook `narrativeHooks:create`，无关联 ID。
- `batchUpsert` 重抽会删 `source_decision_id IS NULL` 的 facts，hooks 只增不换。
- `createProposals` 强制 `requireAssistantSource`（必须是已落库的 assistant 消息），写章抽取无法进账本。
- `foreshadowings` 面板仍在，与账本无关。本轮不删除面板，只保证自动抽取不写它。

### 3. 修改方式

**产品规则（请确认）：**

| 抽取类型 | 写章后立刻做什么 |
|---|---|
| 普通事实、角色知识 | 仍 `batchUpsert` / `batchUpsertKnowledge`（`chapter_extraction`），按章可替换 |
| `factType === 'hook'` | **不**写入 `story_facts`/`narrative_hooks`。改为 `creative_decisions` 状态 `proposed`（`narrative_hook`） |
| 债务 | **本轮不抽。** 对话账本仍可提议 `narrative_debt`；写章 JSON 无 debt 类型，不映射、不落 `narrative_debts` |
| 旧 `foreshadowings` | 不写 |

作者在现有决策面板确认后，由已有 `confirmMany` 投影到 hooks。这保持「抽取自动、落运行时需确认」。

**P2（另立，不在本批次）：** 若产品要「写章也抽债务进待确认」，必须同时改 `FACT_EXTRACTION_SYSTEM_PROMPT`（独立 debt 字段：`debtType`、`subject`、`description`、可选 `promisedByChapter`）、解析类型、以及 `factsToDebtDrafts`。禁止把 hook 事实猜成债务——两者语义不同（钩子是埋下的悬念，债务是故事欠读者、通常带兑现章号）。

**仓储：**

新增 `createChapterExtractionProposals`（或扩展 `createProposals`）：

- 允许 `sourceThreadId` / `sourceMessageId` 为 `null`。
- **不**走 `requireAssistantSource`。
- 仍走 `validateDraft`、`requireNoPendingTarget`（同项目同 target 只能一个 pending）。
- `rationale` 固定为 `章节抽取：{chapterId}` 或章标题。
- payload 本轮只用现有 `narrative_hook` 形状（含 `subject`，v19 已要求）。`narrative_debt` 形状留给对话账本与 P2，写章映射不产出。

对话来源的 `createProposals` 行为不变，继续要求 assistant 消息。

**渲染：**

`onPersistExtraction`：过滤 `factType === 'hook'`，映射为 drafts，调用新 IPC。对话面板的决策 loader 会在下次刷新看到 proposed。写章结束后若决策面板已打开，触发一次 `findByProject` 刷新（可复用 Chat 里已有 loader；若 Chat 未开，下次打开即可见）。

**不做：** 扫描并删除历史上重复的 hooks（避免误伤作者手动钩子）。可在确认后的文档里写「已知旧数据可能重复，不自动清洗」。
