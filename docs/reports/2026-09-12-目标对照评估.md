# hi-story 目标对照评估

- **日期：** 2026-09-12
- **前提：** 前一份《项目技术审查报告》仍然成立。本文只回答一件事：对照未来目标，哪些必须现在改，哪些可以以后改，哪些不要动。
- **产品定位：** AI 小说生产管理系统（不是聊天玩具，也不是纯编辑器）

**一句话结论：** 方向和底座对，50 万字在 SQLite 里存得下。当前架构**还不能称为生产管理系统**，卡点不是技术栈，而是：资料没有单一权威源、写章落库不可靠、钩子双轨、章节历史只留 7 天、长篇 AI 仍按「把能拿到的都塞进 prompt」。

先把这几件做完，再堆新功能。否则 50 万字项目会积累不可逆脏数据。

---

## 目标总览

| 目标 | 现状能否支撑 | 一句话 |
|---|---|---|
| 1. 作者管理世界观 / 人物 / 大纲 | 能用，不能当唯一圣经 | 表和导入都在；三套大纲会在长篇里互相打架 |
| 2. AI 辅助讨论剧情 | 能聊，容易聊偏 | 会话已落库；讨论吃的是写作大纲面板，不是策划总纲 |
| 3. AI 生成章节 | 能生成，不能稳落库 | 代写面板在；保存走 setTimeout 猜章节 |
| 4. 自动提取钩子和债务 | 能抽，会抽重复 | 账本设计对；写章旁路双写且不经确认 |
| 5. 修改历史追踪 | 只覆盖正文章节，且太短 | 每章 30 份 / 7 天；设定和纲没有历史 |
| 6. 长期 50 万字项目管理 | 存储够，生产链路不够 | 50 万字约 1MB 正文，桌面内存不是瓶颈；AI 上下文和权威源才是 |

## 分目标说明

### 1. 作者管理世界观 / 人物设定 / 大纲

**已有：** `characters`、`world_entries`、策划工作台、写作侧 `outline_nodes`、Obsidian 只读 + 单向导入。覆盖策略（keep/fill/replace）和锁定保护是对的。

**不能支撑生产的地方：** 作者改「大纲」时，系统里有三份——策划 JSON、大纲面板、Obsidian。AI 讨论和批量代写读的是 `outline_nodes`，策划页读 JSON。50 万字写到一半，一定会出现「我明明改了总纲，模型还按旧面板大纲写」。

人物 / 世界观本身正规化，够用。世界观 `category` 六类 CHECK 以后加类型会痛，但不是现在的阻塞。

### 2. AI 辅助讨论剧情

**已有：** 按项目持久化的会话、Skill 路由、有界上下文、创作决策从对话里整理提议。

**不能支撑生产的地方：** 讨论如果看不到策划总纲 / 分卷 / 章纲，它就不是在帮这本书工作，而是在帮另一份大纲工作。钩子预算在 `ContextBuilder` 之后追加，长篇讨论会越来越吵。流无法取消是体验问题，不是数据问题。

### 3. AI 生成章节

**已有：** 代写面板、章纲快照（`chapters.planning_outline`，施工卡思路正确）、最近 10 章摘要、事实 / 知识 / 钩子注入。

**不能支撑生产的地方：**

- 保存旁路：`create` 之后用 `sortOrder` + 多层 `setTimeout` 猜刚创建的章。批量代写会连续踩这条路径。
- 生成上下文默认喂 **全部** `outline_nodes` 和 **全部** 人物 / 世界观，而不是当前章的策划章纲。
- 从策划「AI 代写」进来时有章纲快照，批量写仍走大纲面板。

章纲快照这个设计要留：生成时所依据的纲必须冻在章节上，否则改纲会改写历史解释。

### 4. 自动提取钩子和债务

**已有：** 两条路。

1. **决策账本（更好）：** AI 提议 → 作者确认 → 单事务写入 hooks/debts/facts，带 effect 快照。
2. **写章抽取（更危险）：** 生成后自动 `batchUpsert` facts，并把 hook 再 `create` 到 `narrative_hooks`，不检查成功、不经确认、与 facts 无关联。重抽 facts 时钩子只增不换。

「自动提取」作为生产系统，建议保持：**抽取可以自动，写入运行时状态必须可确认或至少可撤销。** 现在最差的是自动写入还写错地方。

旧 `foreshadowings` 面板与账本无关，作者会在错误的地方管钩子。

### 5. 修改历史追踪

**已有：** `chapter_history`，正文变更时打快照；写作区可恢复；UI undo 管实体删除。决策确认有 before/after effect。

**不能支撑生产的地方：**

- 每章最多 30 份，**超过 7 天删除**。50 万字是数月工程，一周后无法回答「这章上个月什么样」。
- 只追踪章节正文。总纲、分卷、人物、世界观、钩子没有版本。生产管理系统里，「设定何时被改」和「正文何时被改」同等重要。
- 没有「这次生成用了哪版章纲 / 哪个模型」的生成记录（施工卡是内容快照，不是操作审计）。

### 6. 长期 50 万字项目管理

先把量级说清楚，避免过度设计：

- 50 万汉字 ≈ 1MB 量级正文。SQLite + WAL 完全够。
- 约 200–400 章（按每章 1500–2500 字）。把全部正文加载进 React，在桌面端通常仍可接受。
- **真正的上限是模型上下文**，不是磁盘。系统已经在用摘要 / 事实 / 近章，方向对；但权威源错误、事实只取最近 30 条、钩子双轨堆积，会在 10 万字之后明显失真。

现在不要做：章节分页、把策划 JSON 拆成正规化表、上 Redux。那些是 100 万字或设定条目到数百条之后的事。

## A. 必须现在修改

判据：不改就会在继续写 / 继续生成时产生脏数据，或让目标 1–4 互相矛盾。这些都是小改或规则改，不是换架构。

| ID | 改什么 | 对应目标 | 为何不能等 |
|---|---|---|---|
| A1 | 写章落库改为 `create` 返回的章节 ID 同步写正文 / 摘要 / 事实；去掉套娃 timer 和 `sortOrder` 猜测 | 3、4、6 | 这是生产主路径。批量代写会连续写错章或丢抽取 |
| A2 | 策划长任务 `await` 后校验仍是原项目；否则丢弃结果 | 1、3 | 切项目会把 A 书的方案写进 B 书 |
| A3 | `planning_ideas.project_id` 加 `UNIQUE`；坏 JSON 报错，禁止静默变空 | 1、6 | 全书圣经不能读错行、也不能解析失败就变没了 |
| A4 | **先定规则再接线：** 策划 JSON 是结构权威。讨论和生成必须读策划章纲 / 总纲，而不是只喂 `outline_nodes`。写作大纲面板可暂时留着，但 AI 不得再拿它当圣经。**落地收窄：** A4a 对话已切策划；A4b 本轮只做策划入口代写 + 审稿改读章纲。工具栏代写/批量接章纲另立 P2 | 1、2、3、6 | 不定权威，后面每加一个 AI 功能都会再分叉 |
| A5 | 钩子只走 `narrative_hooks`（经确认）。写章抽取不要无关联双写 facts+hooks；抽出的 hook 进 `proposed`，不要直接当已确认运行时状态。债务表权威仍是 `narrative_debts`，但**写章抽取本轮不产债务**（对话账本已能提议债务；写章抽债务另立 P2） | 4、6 | 否则 50 万字后钩子列表不可信，AI 预算被垃圾填满 |
| A6 | 章节历史保留策略改为覆盖成书周期（至少按项目保留，或 90 天 / 取消 7 天上限，30 份上限可再议） | 5、6 | 7 天窗口与「长期项目管理」直接冲突；改常量即可，拖到半年后历史已经没了 |

**明确不包括在 A 里：** 拆 `App.tsx`、正规化策划表、typed IPC、合并 CLAUDE/AGENTS、世界观加类别。那些不改也能开始按生产系统用，只是开发会慢。

## 对「生产管理系统」的架构含义

六个目标合在一起，其实是一条流水线：

```
资料权威（人物/世界/纲）
    → 讨论（读同一份权威）
    → 生成章节（按章纲 + 近章 + 未收钩子）
    → 提取钩子/债务（提议，作者确认）
    → 历史可回放（正文长期保留；设定以后再做版本）
```

当前代码里，每段都有零件，但**没有焊成一条管**：

- 资料权威有三份
- 讨论和生成读的不是策划
- 生成结果落库不可靠
- 提取写进两张互不认识的表
- 历史 7 天过期

焊管（A1–A6）优先于换零件（B1–B8）。

## 建议的讨论拍板（给另一位开发者）

在写代码前只需对齐三句话：

1. **大纲圣经 = 策划 JSON。** 对话与策划入口代写不再把 `outline_nodes` 当圣经。工具栏代写/批量仍读大纲面板，接章纲是 P2。面板可以后删。
2. **钩子圣经 = `narrative_hooks`；债务圣经 = `narrative_debts`。** 写章自动抽取目前只产钩子，默认进待确认，不进旧伏笔表。债务由对话账本提议确认；写章自动抽债务是后续 P2，不是 A5 缺口。
3. **下一轮只做 A1–A6。** 不拆 App、不拆策划表、不做 Obsidian 回写。

B9 的三个小 bug（`systemPrompt`、缓存键、审稿 `'current'`）可以顺手修，但不算架构议题。
