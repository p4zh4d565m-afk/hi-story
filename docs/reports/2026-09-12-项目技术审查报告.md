## 1. 当前项目架构总结

这是本地单用户桌面应用，不是 Web SaaS。分层表面上清楚，契约层没有收口。

```
渲染进程 (React + Vite/ESM)
  App.tsx 持有几乎全部实体状态
  各 Panel 自管会话 / 策划 / 决策草稿
        │  window.electronAPI.invoke(任意 channel)
        ▼
Preload  无白名单透传
        ▼
主进程 (CommonJS)
  ipc/*.ipc.ts  →  repositories  →  SQLite (better-sqlite3, WAL)
  AI Provider / SkillRegistry / Obsidian 只读扫描
```

### 1.1 技术栈

| 层 | 技术 |
|---|---|
| 壳 | Electron 33 |
| 渲染 | React 18 + Vite/ESM + Tailwind + TipTap |
| 主进程 | TypeScript CommonJS（`tsconfig.main.json`） |
| 数据库 | better-sqlite3，WAL，`foreign_keys=ON` |
| AI | Anthropic SDK + OpenAI 兼容供应商 |
| 测试 | Vitest + 若干真实 DOM / 隐藏 Electron 窗口回归 |

构建要点：`npx vite build` 只验证渲染打包；主进程与 preload 用 `npm run build:main`。`tsconfig.main.json` 必须包含 `src/preload/**/*`，否则桥接代码不会更新。

### 1.2 文件组织

```
src/main/          主进程：生命周期、IPC、仓储、AI、Obsidian、Skill
src/preload/       contextBridge，泛型 invoke/on
src/renderer/      React 应用；types 同时被主进程引用
resources/         literary.db、writing-skills、obsidian-templates
tests/             unit + ui 回归（Obsidian 导入与决策账本最密）
```

没有 `src/shared`。这是后面「扩展困难」的根之一。

### 1.3 状态管理

没有 Redux / Zustand。

| 位置 | 内容 |
|---|---|
| `App.tsx`（约 1380 行） | 章节、大纲节点、人物、世界观、关系、面板开关、Obsidian 快照、AI 运行时上下文 |
| `useProject.ts` | 项目列表 + 当前项目 + selectionGuard |
| `PlanningWorkspace` | 策划全流程本地 state |
| `AIChatPanel` | 会话线程、流式、决策列表、AI 配置 |
| `WritingArea` | 待保存草稿 Map、保存状态机 |
| `localStorage` | AI 配置、创作罗盘、风格指纹、若干 `hi-story-pending-*` 旁路 |

项目切换用「项目 ID + generation」过滤迟到**读**回执。写路径覆盖不完整。

### 1.4 数据流与 IPC

```
UI 操作
  → window.electronAPI.invoke(channel, ...args)
  → ipcMain.handle
  → Repository
  → SQLite
  → IpcResult<{ success, data?, error? }>
```

约定：渲染端必须检查 `res.success`。保存 / 加载 / 会话 / 决策主路径基本做到了；人物、世界观、大纲的删除与改名大量未检查。

规模：约 **20 个 IPC 模块、128 个 handler**。preload 把任意字符串 channel 透传给 `ipcRenderer.invoke`，没有 typed client。对单机应用，这首先是维护问题，其次才是安全问题。

### 1.5 AI 调用方式

渲染端组装 `ProviderConfig`（含明文 API Key）经 `ai:chat` / `ai:chatStream` 送进主进程。上下文有两套拼装：

- `src/main/ai/context-builder.ts`：普通对话
- `src/renderer/services/ai-prompts/*` + 各 Panel：写章 / 审稿 / 策划 / 润色

`ContextBuilder` 有约 16000 token 预算；`App.tsx` 在 `build` 之后再追加钩子/债务 system 消息，**不计入**该预算。

### 1.6 层违规（会持续放大成本）

- 主进程从 `src/renderer/types` 引类型；`tsconfig.main.json` 为此把 renderer types 编进主进程产物。
- 渲染端直接 `import` 主进程的 `ContextBuilder`。Vite 能打包，职责却反了。

## 2. 已实现功能总结

这些是产品已经交付、且大体能工作的能力，不是待办。

| 域 | 内容 | 成熟度 |
|---|---|---|
| 写作 | 章节 CRUD、TipTap、防抖保存、失败重试、策划/写作切换保活编辑器 | 高 |
| 策划 | 故事方向 → 总纲 → 分卷 → 章纲 → 自己写 / AI 代写，含锁定 | 中（JSON 文档模型） |
| Obsidian | 只读扫描 + 单向导入策划/人物/世界观，含覆盖策略与 stage 归堆 | 高（测试最密） |
| 运行时事实 | 故事事实、角色知识、钩子、债务、创作决策确认账本 | 中高（与旧伏笔脱节） |
| AI | 对话、代写、审稿、润色、起名、Skill 路由 | 中（预设复制、上下文分叉） |
| 其它 | 人物/世界观/关系图、素材、参考库向量、全书文风统计、导出备份 | 不均 |

测试分布能说明健康区：Obsidian 导入和决策账本有大量单测 + UI 回归；`App.tsx` 写章旁路、`PlanningWorkspace` 长任务、Provider 缓存几乎没有回归网。

章节保存已经过硬化，不要当重构入口：

1. `RichEditor` 按 `activeChapter.id` 重建
2. 按键时捕获章节 ID，防抖到期再核对
3. 切章立即 flush
4. `handleSaveChapter` 检查 `res.success`
5. 策划/写作切换用 `hidden` 保活，不卸载编辑器
6. 保存失败保留草稿并重试

## 3. 发现的问题

### 3.1 严重

#### S1. 三套大纲长期并存

| 源 | 用途 |
|---|---|
| `planning_ideas` 三列 JSON | 策划工作台、拆章 prompt、正文施工卡来源 |
| `outline_nodes` | 写作侧大纲面板；`ContextBuilder` 注入普通对话 |
| Obsidian Vault | 只读优先摘录；导入写入策划/实体 |

拆章会注入策划 `stages`；写正文和普通对话故意不采用。改策划不等于改对话里的大纲，改大纲面板不等于改章纲。每加一条 AI 通路都会再分叉一次。

**证据：** `src/main/db/repositories/planning.repo.ts`、`outline.repo.ts`、`src/main/ai/context-builder.ts`（约 182–203 行）

#### S2. 伏笔 / 钩子双轨

- `foreshadowings`：手动伏笔面板（迁移 v7）
- `narrative_hooks` / `narrative_debts`：决策账本投影（v18/v19）
- AI 写章旁路把 `factType=hook` 同时写入 `story_facts` **和** `narrative_hooks`，两者无关联 ID
- 章节重抽会替换 facts，钩子只增不换 → 重复堆积

**证据：** `src/renderer/App.tsx` 约 1337–1357 行；`creative-decision.repo.ts` 明确不写 `foreshadowings`

#### S3. `App.tsx` 是唯一实体仓库

约 1380 行。章节、人物、世界观、关系、Obsidian、参考检索、菜单导出、AI 写章落库都经过这里。新功能几乎必改此文件，回归面随功能线性膨胀。

次级大块（实体真相仍回灌 App）：

- `AIChatPanel.tsx` ~1246 行
- `AIWritePanel.tsx` ~952 行
- `AIReviewPanel.tsx` ~946 行

`useChapter.ts` 无人引用，是死代码且保存不检查 `success`。

#### S4. 策划层巨型 JSON，且无项目唯一约束

全书结构塞进 `planning_ideas` 三列：

- `master_outline`
- `volume_outlines`（`stages` 再嵌套其中，**无独立表、无迁移**）
- `chapter_outlines`

问题：

1. 无内部 `_schemaVersion`，字段变更无法做数据迁移
2. `rowToPlanningIdea` 对坏 JSON `catch` 后变成空数组 / `null`，损坏表现为「纲没了」而不是报错
3. `PlanningRepo.save` 未传的字段写成 `[]` / `''`（当前 UI 总是传全量，新调用方会踩雷）
4. schema 只有 `idx_planning_ideas_project`，**没有 `UNIQUE(project_id)`**
   - 日常仓储：`ORDER BY updated_at DESC LIMIT 1`
   - Obsidian 导入：`rows.length > 1` 直接抛错
   - `buildTargetState`：`planningRows[0]`，无 `ORDER BY`

两套代码对「哪一行是真相」定义不同。一旦写出第二行，日常策划看起来正常，导入永久阻断。

**证据：** `src/main/db/migrations.ts` v11；`planning.repo.ts` 23–54、97–100 行；`obsidian-import.repo.ts` 约 34、325 行

#### S5. 策划 AI 生成可污染其他项目（已核对）

`PlanningWorkspace` 在 `App` 里常驻挂载（不随项目卸载）。`generate` / `generateMasterOutline` 等在长 `await` 之后无条件 `setState` + `save`。

切到项目 B 后：

1. A 的生成结果覆盖 B 的界面
2. `save` 闭包仍可能写回 A（数据层面 A 还对）
3. 用户在 B 的界面点「确认」，用 **B 的 `project.id` + A 的 options** 写库 → **跨项目策划数据写坏**

读路径有 generation 守卫，这条写路径没有。

**证据：** `src/renderer/components/PlanningWorkspace.tsx` `generate`（约 157–188 行）、`confirm`（190–197 行）、`generateMasterOutline`（199–227 行）

#### S6. AI 写章落库是定时器旁路（已核对）

`App.tsx` 的 `onSaveAsChapter`：

1. `handleCreateChapter(title)`
2. `setTimeout(300ms)` 再 `findByProject`，按 `sortOrder` 最大猜「刚创建的章」
3. 再套 500 / 800 / 1000ms 写 summary / facts / hooks
4. 不检查 `res.success`
5. `projectId` 用当时的 `activeProject?.id`

并发创建或切项目时可能写错章、静默丢抽取结果、钩子重复堆积。

**证据：** `src/renderer/App.tsx` 约 1309–1375 行

#### S7. 主进程与渲染进程类型双向耦合

没有 `src/shared`。加一个字段要同时让 renderer types、main tsc include、Vite 打包、测试 import 对齐。这是扩展时最隐蔽的税。

**证据：** `tsconfig.main.json` 的 `include`；`App.tsx` `import { ContextBuilder } from '../main/ai/context-builder'`；大量 repo `from '../../../renderer/types'`

### 3.2 中等

#### M1. OpenAI 兼容路径忽略 `systemPrompt`

Claude 会合并 `options.systemPrompt`；`GenericOpenAIProvider` 的 `chat` / `chatStream` 完全不读该字段。起名助手依赖它（`NameGenerator.tsx` 约 502–505 行）。国内常用供应商等于丢系统指令。

**证据：** `src/main/ai/providers/claude.ts`；`src/main/ai/providers/generic-openai.ts`

#### M2. Provider 缓存键缺 `baseUrl`

```ts
return `${config.name}:${config.model}|${apiKey.slice(0, 8)}`;
```

改自定义 endpoint、或两把 Key 前 8 位相同，会复用错误实例（错误 endpoint / 错误 Key）。

**证据：** `src/main/ai/provider-factory.ts` `key()`

#### M3. 审稿接受修订后用字面量 `'current'` 刷新

```ts
const refreshRes = await electronAPI.invoke('db:chapter:findByProject', 'current');
```

保存成功后刷新必然空，作者看不到写回后的章节列表。注意：`refreshRes` 赋了值但后续未使用，真正的章节列表在 App 里也不会因此更新。

**证据：** `src/renderer/components/AIReviewPanel.tsx` 约 484 行

#### M4. 删除 / 改名普遍不检查 `res.success`

保存主路径已检查。人物 / 世界观 / 大纲 / 关系的 `remove` 与 rename 先信 IPC 成功。失败时 UI 与 SQLite 分裂，undo 会放大。

**证据：** `App.tsx` 多处；`useProject.ts` 的 `deleteProject`

#### M5. 上下文预算可被旁路追加突破

`ContextBuilder.build` 有 16000 token 预算。`App.tsx` 约 1106–1111 行在 build **之后**再追加 `narrativeContext` 第二条 system 消息。写章 / 审稿另有一套拼装，不走同一预算器。

#### M6. `ai_configs` 表是死表，密钥在 localStorage

v1 建了 `ai_configs`，全仓无 `INSERT`。运行时读 `hi-story-ai-configs`。创作罗盘、风格指纹同样在 localStorage（`ContextBuilder.getCompassContext` 用 `globalThis.localStorage`，放在 main 模块里，职责错位）。

`safeStorage` 不可用时 **明文回退**（`src/renderer/services/crypto.ts`）。换机或清站点数据会丢配置，与「SQLite 为权威」叙事冲突。

#### M7. 供应商预设复制了 5–8 份

同一 baseUrl / 模型表出现在 `provider-factory.ts`、`AIChatPanel`、`AIWritePanel`、`AIPolishPanel` / `AIReviewPanel` / `ContextPanel`、`PlanningWorkspace`、`App.tsx`。Chat 面板没有 `custom` preset。加一个供应商容易漏改。

#### M8. 字符串 IPC 无类型客户端

preload：

```ts
invoke: (channel, ...args) => ipcRenderer.invoke(channel, ...args)
```

对单机应用，XSS 攻击面不是主矛盾。真正的长期成本是约 128 个 handler 全靠约定，拼写无编译期检查。

附带：`import:parseFile` 接受任意 `filePath`，无对话框路径校验；多数 `update/remove` 只认 id，不校验项目归属。单机场景可后置，不要做成安全大改。

## 4. 潜在风险

1. **静默丢纲。** 策划 JSON 损坏，或 `save` 漏传字段，会清空全书结构。当前 UI 总是传全量，新 IPC 调用方很容易踩。
2. **跨项目写坏策划。** S5 是用户可操作路径，不必等极端并发。
3. **钩子膨胀污染 AI 预算。** S2 + S6，追读力上下文会越来越吵。
4. **AI 对不上作者正在看的纲。** 对话吃 `outline_nodes`，策划页吃 JSON。作者会觉得「模型没看总纲」。
5. **换机丢配置。** 密钥和罗盘不在 SQLite；备份导出也不含策划。
6. **流式无法取消。** 切项目后主进程请求继续跑，浪费额度。
7. **本地安全（次要）。** 任意 channel 透传 + 任意路径读文件。优先当维护问题，不要做成安全大改。

## 5. 技术债列表

| 债 | 为何要还 | 不还会怎样 |
|---|---|---|
| 大纲权威源未声明 | 每个新 AI 入口都要再决定读哪份 | 双份真相变成三份、四份 |
| 策划 JSON 无 schema 版本 | 下一层结构只能「改 TS + 默默兼容」 | 无法做数据迁移 |
| `planning_ideas` 无唯一约束 | 两套读法已经不一致 | 导入永久阻断或读错行 |
| App 单体 store | 功能线性增加回归面 | 人人都不敢动保存 / 切项目 |
| 无 `src/shared` + 无 typed IPC | 契约靠字符串和口头 | 改字段漏一层就运行期才炸 |
| Provider / prompt 多入口 | 加供应商、加任务类型要改一串文件 | 漏改表现为「这个面板能用、那个不能」 |
| `localStorage` 旁路协调 | `hi-story-pending-*` 无代次 | 幽灵副作用，难测 |
| 死表 `ai_configs`、死 hook `useChapter` | 误导后续开发者 | 走错保存路径导致丢正文 |
| 素材 SQL 写在 IPC | 仓储边界被打破 | 新实体会继续复制这种写法 |
| 双份 AGENTS / CLAUDE | AI 开发者按过期约定实现 | 文档比代码更危险 |

## 6. 哪些地方未来扩展会困难

### 加第四策划层（例如「场景卡」）

要动：迁移或再嵌一套 JSON、`PlanningRepo.save` 全量覆盖语义、`PlanningWorkspace` 状态机、prompt、Obsidian 识别 / overlay、以及「写章 / 聊天是否注入」的产品决定。`stages` 已经证明：每加一层都要在多条 AI 通路上重复声明采纳规则。

### 加新实体（例如「势力」「道具」）

要动：迁移、repo、IPC 注册、`App.tsx` state、`project-data-loader`、types、UI；若进 AI 则 `ContextBuilder` + 各面板 props；可选导出 / 导入。没有实体插件点。

### 加新 AI 任务

prompt 文件 + 某个约 1000 行的 Panel + 可能的 runtime loader。没有单一装配点，token 预算不统一。

### 加新供应商

至少改 `provider-factory` 和 4–6 个面板硬编码表，还要处理 embedding 支持表。Chat 与 Write 的 preset 已经不一致。

### 正规化查询策划结构

「列出某卷全部 stages / 按章号找章纲」现在只能把整份 JSON 读进内存。JSON 列在编辑体验上够用；一旦要检索、引用、部分更新，就会卡住。

## 7. 哪些代码需要重构

重构目标是**收口边界**，不是把大文件切小。

| 优先 | 对象 | 做法 | 不要做 |
|---|---|---|---|
| 立刻修，不大拆 | `PlanningWorkspace` 长任务 | `await` 后校验 `currentProjectIdRef` | 重写策划 UI |
| 立刻修 | `App.tsx` `onSaveAsChapter` | `create` 返回 ID 后同步写内容 / 摘要 / 事实 | 继续用 sortOrder + setTimeout |
| 立刻修 | `planning.repo` + 迁移 | `UNIQUE(project_id)`；坏 JSON 失败可见 | 现在就拆成多表 |
| 立刻修 | `generic-openai.ts` / `provider-factory.ts` | 读 `systemPrompt`；缓存键含 `baseUrl` | 换 SDK |
| 短期 | 大纲与伏笔 | 声明权威源，另一份派生或停用 | 写同步双向管道 |
| 中期 | `App.tsx` | 抽出 `useChapters` / `useEntities`（复用现有保存纪律） | 上 Redux |
| 中期 | 类型与 IPC | `src/shared` + channel 字面量联合类型 | 为「安全」做完整 allowlist 大改 |

## 9. 推荐优化路线

不要并行开三场重构。顺序如下。

### 第 0 步 — 堵会写坏数据的洞（大约几天，几乎不动架构）

- 策划生成 / 总纲 / 分卷 / 章纲在 `await` 后检查仍是原项目，否则丢弃结果
- 写章用 `create` 返回的章节 ID 同步更新，去掉 localStorage + 套娃 timer
- 迁移给 `planning_ideas.project_id` 加唯一约束并清理重复行
- OpenAI 路径合并 `systemPrompt`
- 缓存键加入 `baseUrl`
- 审稿刷新传入真实 `projectId`
- 坏 JSON 报错，禁止变空

### 第 1 步 — 只定一个大纲真相、一个伏笔真相

建议的产品规则（讨论用，不是已拍板）：

- **策划 JSON 是结构权威**
- `outline_nodes` 降为派生，或逐步停用写作侧大纲面板
- AI 写章继续用章纲快照（施工卡，保留合理）
- 普通对话不要再只喂 `outline_nodes`
- 伏笔 UI 接到 `narrative_hooks`，停止无关联的 facts+hooks 双写
- JSON 增加 `_schemaVersion`

这一步是架构声明，不是大搬家。

### 第 2 步 — 拆 App 的状态，不换界面

把章节 / 人物 / 世界观 / 关系从 `App.tsx` 挪到 hooks，保存纪律（检查 `success`、项目守卫）跟着走。App 只负责编排 Dock。不要为了规范引入新状态库。

### 第 3 步 — 收口契约

- `src/shared` 放类型和 channel 字面量
- 供应商预设一份
- 所有 AI 上下文走同一 assembler
- 导出补上策划和账本
- `CLAUDE.md` / `AGENTS.md` 合一份，或自动生成其中一份

### 现在不要做

- 把策划 JSON 正规化成 volume / chapter / stage 表（等真的要按阶段查询再说）
- Obsidian 回写
- 重写 TipTap 保存
- 以安全为名重做整条 IPC 栈
- 上 Redux / Zustand「为了规范」
